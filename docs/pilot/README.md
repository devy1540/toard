# 3~5개 팀 파일럿 운영안

상태: 모집·연락·실사용 검증 전. 아래 목표는 측정 기준 제안이며 달성 결과가 아니다. 외부 연락과 서비스 배포는 사용자 승인 후 진행한다.

파일럿의 질문은 “기능이 많아 보이는가”가 아니라 **팀이 기록을 믿고 반복해서 확인하며 실제 운영 판단에 쓰는가**다. 서로 다른 OS와 최소 두 종류의 AI 도구를 쓰는 팀 3~5곳을 대상으로 2주간 진행한다. 팀별 담당자 한 명과 참여자 수, 도구/OS 조합만 필요한 범위에서 기록한다.

## 시작 전

- [업그레이드 안내](../trust-roadmap-upgrade.md)의 배포 gate와 복원 절차를 확인한다.
- 각 팀이 데이터 소유자·보존 범위·접근 권한을 정한다. 개인 프로젝트는 제외하고 본문 수집은 기본적으로 끈 상태에서 시작한다.
- 비용은 실제 청구액이 아닌 API 환산액이라고 설명한다. 활용 지수나 토큰 수를 직원 평가 자료로 사용하지 않는다.
- 사용자에게 [참여 안내](participant-guide.md)와 [피드백 양식](feedback-template.md)을 제공한다. 토큰·비밀번호·대화 본문·개인 경로를 피드백으로 받지 않는다.

## 2주 진행

| 시점 | 실행 | 남길 증거 |
|---|---|---|
| 시작일 | 초대, 로그인, 컴퓨터 연결, 로컬 범위 검토, 첫 저장 | 시작/완료 시간, 실패 단계, 민감정보 없는 오류 코드 |
| 1~3일 | 평소 업무에서 사용하고 수집 상태 확인 | 누락 의심 사례, 인식된 도구·버전, 해결 시간 |
| 1주 말 | 첫 주간 보고서와 CSV 확인 | 스스로 확인한 횟수, 이해하지 못한 숫자, 실제 사용한 판단 |
| 2주 | 수정 후 재확인, 합성 데이터로 장애 복구 검증 | 전송 전후 고유 건수, 중복/손실 여부, 재시도 결과 |
| 2주 말 | 두 번째 보고서 확인 및 유지/중단 결정 | 다시 쓸 이유, 중단 이유, 필요한 한 가지 개선 |

## 제안하는 통과·중단 기준

- 온보딩: 참여자 90% 이상이 담당자의 직접 DB/파일 수정 없이 첫 저장을 확인한다. 목표 시간은 설치 명령 실행 후 10분 이내다.
- 신뢰성: 합성 fixture 장애 시험에서 이미 commit한 사용량의 손실과 서버 중복 집계가 모두 0이다. 금액 표본 5건 이상에서 표시 근거와 계산을 재현할 수 있다.
- 이해도: “연결됨/저장됨”, “API 환산액/청구액”, “미확정/0”의 차이를 참여자가 설명할 수 있다.
- 반복 사용: 팀 담당자가 두 주 모두 보고서를 자발적으로 확인하고, 최소 한 번은 데이터로 질문이나 운영 판단을 구체화한다. 단순 로그인 횟수만으로 성공을 판정하지 않는다.
- 중단: 동의하지 않은 프로젝트·본문 전송, 권한 밖 열람, 설명되지 않는 중복/손실이 발견되면 모집 확대를 멈추고 재현·복구부터 진행한다.
