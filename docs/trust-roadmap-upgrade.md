# 가입·가격·수집 개선 릴리스 전환

이 안내는 이 브랜치의 0.0.3 릴리스 후보를 배포할 때 사용할 절차다. 문서 작성만으로 공개 배포나 운영 검증이 끝난 것은 아니다. 운영 DB를 직접 수정해 상태를 맞추지 않는다.

## 배포 전 확인

1. 현재 서버·shim 버전, PostgreSQL/ClickHouse 사용 여부, 실제 공개 URL을 기록한다. 사용 중인 백업 절차로 DB와 필요 시 ClickHouse 백업을 만들고 별도의 테스트 환경에서 복원을 검증한다. 시크릿이나 실제 대화 본문을 검증 artifact에 넣지 않는다.
2. 같은 버전의 소스·이미지·shim을 릴리스 artifact로 준비한다. `pnpm verify:release-version`, `pnpm typecheck`, `pnpm test`, `pnpm test:browser`와 shim의 fmt/clippy/test를 실행한다. 릴리스 가이드가 요구하는 플랫폼·배포·성능 gate도 확인한다.
3. 로그인 관리자 계정과 복구 경로를 확인한다. 새 설치의 관리자 이메일·비밀번호는 사용자가 지정해야 한다. 기존 `AUTH_SECRET`을 임의 교체하지 않는다. 프로덕션용 scheduler에는 `CRON_SECRET`을 설정한다.

## 적용 순서

1. `capabilities --scope`가 `collection-scope-v1`을 반환하는 shim을 먼저 게시한다. 새 웹 설치 화면은 기본 review 경로에서 이 기능을 요구하므로 구버전 shim만 내려받는 상태로 UI를 먼저 공개하지 않는다.
2. 테스트 환경에서 migration `1700000054`와 `1700000055`를 적용한다. 가격 세부 근거·계산 버전·estimated 상태, 저장 receipt 및 수집 상태 table이 대상이다. 상세 SQL은 `migrations/`의 파일을 따른다.
3. 새 앱을 배포한다. 이전 repricing worker와 새 worker가 동시에 서로 다른 알고리즘으로 재계산하지 않게 배포 구성을 확인한다. 첫 관리자는 로그인, 관리자 기능, `/api/health`, `/api/ready`를 확인한다.
4. 신규 가입은 기본 invite-only다. 공개 가입을 운영하려면 verified OAuth 정책을 명시적으로 선택한다. 이메일 문자열만으로 가입하던 이전 흐름을 정상 동작으로 기대하지 않는다.
5. 기존 계산 금액은 `cost-v1`로 보존된다. 일괄 재계산이 끝났다고 가정하지 않는다. ledger와 보고서에서 근거가 부족한 값·추정·미확정을 확인하고 가격 복구 상태를 점검한다.
6. 기기 하나에서 새 설치의 review 등록 → 로컬 범위 선택 → 첫 실제 저장 확인을 검증한다. 이미 보관한 사용량을 대상으로 네트워크 실패와 재전송을 시험한다. 실제 원본 로그를 삭제하는 훈련 대신 합성 fixture를 사용한다.
7. experimental OTLP를 사용하던 기기는 관리 exporter를 해제하고 AI 프로세스를 재시작한 뒤 범위를 적용한다. 사용자 정의 exporter와 서버 provider의 `collection_method`도 확인한다.

## 기능별 확인

- 인증: 미초대 password 가입 거절, 초대 1회 사용, OAuth verified identity, 기존 계정 로그인.
- 가격: API 환산액 표기, price revision과 계산 버전, 미확정/추정 상태. 이전 알고리즘 금액이 새 근거로 잘못 설명되지 않는지 확인.
- 수집: 빈 요청은 연결만 확인하며 첫 저장 완료를 만들지 않는다. 로컬 대기열의 account binding·용량·재전송 상태를 확인한다.
- 범위: 포함·제외한 프로젝트와 미식별 기록이 의도대로 처리되는지 확인한다. 범위 설정용 경로/목록은 로컬 창에서만 조회한다.
- 보고서: 완료된 주와 타임존, 개인/팀/조직 권한, 미확정 금액, CSV 수식 처리, 서버 반영 대기 상태.

## 복구 시 주의

스키마는 forward-only다. 구버전 앱으로 무조건 되돌리거나 볼륨을 삭제하지 않는다. 문제가 발생하면 원본 로그·로컬 SQLite/WAL·DB 백업·실패 로그를 보존하고 새 쓰기를 멈출 범위를 먼저 정한다. 이전 reader가 새 status와 column을 읽을 수 있는지 검증한 경우에만 앱 rollback을 선택한다. 토큰 소유자가 달라진 대기열을 새 계정에 강제 연결하지 않는다.

정적 사이트는 `site/`의 합성 데이터 화면을 게시한 뒤 실제 `/toard/demo/` HTTP 응답과 이미지 표시를 확인한다. 서버 배포와 정적 사이트 게시를 같은 작업으로 간주하지 않는다.
